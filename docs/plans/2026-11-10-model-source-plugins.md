# 模型来源插件：机制与平台代理迁移计划

日期：2026-11-10。

状态：第 3、4 部分的后续实施文档；本轮仅实现第 1、2 部分（统一模型来源、手动 API 接入）。本文中的插件安装、进程通信和平台迁移尚未实现，不能当作现有能力。

## 已确认方向

核心内置手动 API 来源：用户填写 API URL、API Key、模型 ID、上下文窗口、最大输出及图片/推理能力。Agent 与外部工具继续使用本地统一 Chat Completions 网关。平台特有的网页登录、凭据续期、配额/签到、模型发现及私有协议转换从客户端运行链路移出，之后通过安装模型来源插件接入。

本地网关的鉴权、请求取消、流式生命周期和真实用量统计属于核心。上游剩余额度与本地 token 用量是两种数据；没有配额插件时不展示虚构的余额。

## 第 1、2 部分为插件留下的边界

- Source 保存稳定来源 ID、名称、来源类型、协议、地址和启停状态；API Key 仅在服务端加密保存，管理读取只返回是否配置。
- Model 保存稳定内部 ID、所属来源、上游模型 ID、名称、上下文窗口、最大输出与能力。路由使用稳定内部 ID，上游模型名不作为跨来源唯一键，不解析上游 ID 中的 `/` 来猜测平台。
- 手动来源目录只读取用户保存的配置，读取或刷新目录不自动访问上游。
- Agent 只消费统一模型目录与 `/v1/chat/completions`；增添平台来源不要求 Agent 学会平台登录或私有协议。
- 旧平台账号及加密凭据留在原目录，不自动删除、不自动转成手动来源。停用的旧模型引用继续保存在会话和偏好中；调用时明确不可用，由用户选用新模型，不静默重绑到同名模型。
- 原平台实现暂保留作迁移参考，但不从客户端运行入口注册，不启动登录、刷新、配额或目录发现。后续插件迁移验收后再清理旧实现。

## 第 3 部分：最小插件机制

### 交付范围

从本地插件包安装、查看状态、启用、停用与卸载；版本化 manifest、插件进程生命周期、模型来源注册、统一模型调用。第一版不做在线市场、自动下载更新或插件任意前端脚本执行。

优先采用独立进程，通过 stdio JSON-RPC 通信；不依赖 Go 动态插件，兼容 Windows 分发。此传输方案为实施建议，编码前先用一个最小插件完成协议验证。插件不是 MCP 工具，也不是 xt-skills 的宿主 Skill/Hook 安装器；可借鉴进程管理与诊断，不能复用其语义冒充模型来源插件。

### manifest 草案

```json
{
  "id": "example.platform",
  "version": "0.1.0",
  "contractVersion": 1,
  "name": "Example 平台",
  "entrypoint": "bin/provider.exe",
  "capabilities": ["chat", "login", "refresh", "models", "quota"]
}
```

包内入口使用相对路径，安装时校验入口与文件路径，防止越出插件目录；包安装到当前环境专用目录。安装执行代码，需要在产品流程明确展示插件身份和将运行的入口。卸载与删除账号凭据分开，不因卸载静默抹掉用户数据。

### 协议与职责

| 能力 | 建议方法 / 事件 | 约定 |
| --- | --- | --- |
| 初始化 | `initialize` | 协商 contractVersion，返回插件身份、能力和来源表单描述；不兼容明确拒绝 |
| 模型来源 | `sources/list`、`models/list` | 核心分配或验证稳定来源/模型 ID；保留上游 ID 与能力，插件缺失时标不可用 |
| 聊天 | `chat/start`、`chat/delta`、`chat/usage`、`chat/end`、`chat/error` | 必需能力；标准 Chat 输入与工具调用片段；requestId 区分并发请求 |
| 取消 | `chat/cancel` | 核心取消后中断上游，不再接受该请求的迟到片段 |
| 登录 | `login/start`、`login/poll`、`login/cancel` | 可选；核心展示通用状态、授权 URL 与标准表单，插件处理平台 OAuth/设备身份 |
| 凭据续期 | `credentials/refresh` | 可选；凭据版本比较替换，旧请求不可覆盖重新登录结果 |
| 模型发现 | `models/refresh` | 可选；显式操作触发，失败保留上次快照并说明错误 |
| 配额与签到 | `quota/get`、`checkin/status`、`checkin/claim` | 可选；支持才显示，不把用量估算当平台余额 |
| 关闭 | `shutdown` | 停用时停止新请求，处理在途取消并回收直接子进程 |

核心持有版本化 DTO，不让协议类型依赖 `internal/storage` 或某个平台 Credential。插件负责平台身份、请求签名、协议转换、模型映射和平台重试；核心负责凭据引用、状态、取消/超时、统计、生命周期与错误显示。

上游收到首个有效事件后不重放请求或拼接另一个账号响应；usage 只计平台已确认的真实值。进程退出、超时、断流、协议损坏都必须形成失败或中断，不能输出成功终态。错误和日志不携带 API Key、token 或对话正文。

### 凭据和环境隔离

凭据由当前环境密钥环按插件/来源命名空间加密，列表只返回引用与状态。插件通过有范围的凭据接口处理所属来源；这不是对本机插件可执行程序的操作系统级沙箱。

正式版与 UAT 的插件安装、配置、凭据副本、登录会话和进程状态相互隔离。涉及轮换 refresh token 的平台，不应在两环境间自动共享刷新状态；迁移前单独确定导入与重新登录策略，不能直接恢复旧的全平台 UAT 导入流程。

### 第 3 部分验收

- 使用无真实账号的示例插件，验证安装/启停/卸载、错误版本、缺失入口、坏 manifest 与越界路径。
- 验证多来源同名模型不冲突，模型 ID 经插件重启和更新保持稳定。
- 验证流式文本、reasoning、工具参数增量、非流式结果、真实 usage、上游错误、进程崩溃与主动取消。
- 验证停用/卸载后旧会话可查看，发送时明确不可用，不转向其他同名模型。
- 验证正式版/UAT 隔离；前端覆盖加载、失败、键盘、窄屏、主题与减少动态效果。

## 第 4 部分：原平台代理迁移

### 迁移顺序

先选择一个拥有可用验收账号、协议相对简单的平台完成端到端样板；WorkBuddy 标准 Chat 请求链路可作为候选，但实际顺序以可用账号为准。样板稳定后，再迁移 Trae、Codex、Qoder、Antigravity。顺序为建议，不代表这些插件已经支持。

### 迁移清单

| 旧实现 | 插件承接内容 | 重点回归 |
| --- | --- | --- |
| `internal/authsessions` 与 app 登录路由 | 登录会话、OAuth/设备授权、取消与手动回调 | state 校验、过期、取消、重新登录 |
| `internal/providers/workbuddy` | 国内原生登录、标准 Chat、模型目录、配额/签到 | 使用原生渠道，不误读旧 CodeBuddy 凭据 |
| `internal/providers/trae` | 身份、chat_v3、模型窗口/档位、额度/签到 | 工具历史、Max 变体、缓存用量 |
| `internal/providers/codex` | OAuth、Responses 转 Chat、目录/配额 | refresh token 轮换、工具增量、断流 |
| `internal/providers/qoder` | 国内/海外授权、COSY、目录/配额/活动 | 区域隔离、10605 排队、刷新竞争 |
| `internal/providers/antigravity` | Google 身份、Gemini 封装、签名缓存、目录/配额 | thoughtSignature、首事件前降级、已输出不重放 |
| `internal/proxy` 平台分支与账号服务 | 续期协调、平台专用目录映射和冷却重试 | 凭据版本比较、不复活已删账号 |

### 旧数据与模型引用

1. 读取原 `accounts/accounts.json` 和对应密钥环，先做只读识别和用户可见的迁移预览，不因升级自动改写旧账号。
2. 用户安装对应插件并执行迁移后，将凭据在当前环境密钥环内重新保存；不可自动转换的身份要求重新登录。
3. 为旧平台模型 ID 生成可审查的映射。只在平台、账号和上游模型均可确定时迁移；重名或缺失不猜测。
4. 会话历史保持原文和原模型记录；需要切换执行模型时由用户明确选择。是否批量迁移常用/默认模型作为单独操作，不直接改写历史参数快照。
5. 插件卸载后保留账号数据，明确标为插件未安装；删除凭据需要独立删除操作。
6. 迁移通过后才删除对应旧代码及失效测试、清单和规则；历史协议文档作为档案保留并标明状态。

### 每个平台的完成条件

安装与登录、模型目录、流式/非流式、工具调用、取消、凭据续期和真实用量全部通过隔离回归；具备能力的平台还需配额/签到回归。至少完成一次真实账号及 Windows 桌面壳验证，并记录未验证项，不用 mock 结果代替真实平台验收。

## 当前交付与后续关系

第 1、2 部分不以第 3、4 部分完成为前提：用户配置手动 API 后即可使用 Agent 和本地模型 API。插件未实现期间，原平台账号不可继续直接调用。首期只支持 OpenAI 兼容 Chat Completions 上游；Responses 和 Anthropic 专用上游需要后续传输适配或插件，不把填写 URL 等同于兼容所有协议。
