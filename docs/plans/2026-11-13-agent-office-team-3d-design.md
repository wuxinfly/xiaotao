# Agent 办公室：团队与 3D 第一阶段设计

日期：2026-11-13。

状态：已确认方向，尚未实现。本规格描述下一轮客户端交付和共享协议草案；不代表现有客户端、XiaoTao Skill 或 Worker 已具备这些能力。现有能力仍以[阶段一实现](2026-11-12-agent-office-implementation.md)为准。

## 产品目标

客户端是 XiaoTao 协作体系的可视化入口，XiaoTao Skill 是同一体系在受支持宿主中的语义入口。两者最终共享角色、项目成员、工作流程、任务和记忆的含义，不各自维护一份固定团队名单。

第一阶段只打通客户端的成员生命周期和 3D 办公室，同时定义后续 Skill 可读取的角色协议。工作流程编辑、Skill 重构、成员间自主协作和独立子 Agent 运行时不包含在本次交付中。

## 已确认决策

- 办公室使用固定斜视的真实 3D 场景，支持有限缩放和平移，不支持自由旋转或第一人称探索。
- 人物采用低多边形基础造型，提供少量造型和配色选择；模板提供默认外观，用户可以预览和更换。
- 团队管理位于当前项目办公室内，不增加独立团队页面。
- 新项目可通过成员模板快速建队，也可逐个自由创建；模板只生成成员，不绑定或生成流程。
- 模板默认生成项目角色，用户可将认可的成员提升为全局角色。
- 全局角色和项目角色共存；全局角色需加入项目后才出现在该项目的办公室。
- 成员与流程分开建模。流程在后续版本实现，执行阶段必须引用当前项目已加入的成员。
- 第一阶段定义共享读取协议，后续再让 Skill 按该协议发现角色和流程。

## 第一阶段范围

1. 创建、编辑、加入、移出和删除角色。
2. 配置角色名称、职责、模型偏好、3D 造型和配色。
3. 从团队模板生成项目角色，或从全局角色库邀请已有角色。
4. 在当前项目的 3D 办公室中展示团队成员、名称、职责和真实状态。
5. 点击成员查看资料、对话、调整形象或管理团队归属。
6. 保留现有任务、审批、消息、产物和资料架能力。

第一阶段不交付：流程模板、流程编辑器、跨成员自动交接、角色被指定为任务执行者、跨项目记忆共享、复杂捏人、自由镜头、Skill 的实际角色查询和 Worker 协议重构。

## 角色、成员关系与执行实例

### 角色

角色是长期存在的身份与职责配置，包含：

- 稳定角色 ID、名称、职责说明和可选能力标签；
- 模型偏好及可用的模型参数；模型不可用时应提示，不静默宣称使用了指定模型；
- 3D 基础造型 ID 和配色 ID；
- 全局或项目来源、数据版本、创建和更新时间。

角色不是工作流节点，也不是一次模型会话。名称可以修改，稳定 ID 不随名称变化。

### 项目成员关系

办公室展示的是“角色已加入当前项目”的成员关系，而不是复制角色。成员关系记录项目、角色 ID、来源和加入时间，可扩展项目内显示名或项目职责覆盖；第一阶段默认直接沿用角色配置。

- 全局角色的身份、职责、模型和外观在所有已加入项目间复用。
- 编辑全局角色会影响所有项目，保存前明确提示影响范围。
- 项目角色只属于当前项目，不出现在其他项目的可邀请列表。
- 移出项目只解除成员关系，不删除全局角色，也不删除历史任务和对话。
- 删除全局角色是独立操作，需列出受影响项目；仍有成员关系或历史引用时不能静默级联删除。
- 项目角色提升为全局角色时保留稳定身份和现有项目成员关系；移动配置需原子完成，失败不能同时留下两份可用角色或丢失原角色。

### 执行实例

长期角色与 Worker 不是同一概念。角色提供身份和默认职责；Worker 是一次任务的有界执行规格，执行会话是实际运行实例。后续调度时，任务必须显式记录角色 ID、成员关系、Worker 规格快照和执行会话 ID。

第一阶段仍由现有小涛执行者机制完成任务，不能把“角色可对话”描述为“角色已能独立接任务”。新增的角色对话只带该角色的身份与项目边界；无工具对话不得获得项目文件工具。现有执行者的取消、审批和排队消息规则保持不变。

这套角色协议不恢复 Skill 已退役的旧 Role 目录、`role:*` 或 `role_state_path` 执行协议。后续 Skill 重构需单独评审角色与 Worker 的映射、权限和恢复语义。

## 团队管理体验

### 首次建队

已有成员的项目直接进入办公室。没有成员时显示建队引导：

- **使用成员模板**：展示模板内的角色、职责和默认外观，可增删、改名和修改外观后创建；
- **自由创建**：从空团队开始添加项目角色或邀请全局角色；
- **稍后设置**：允许进入空办公室，但团队管理入口保持可见，不伪造团队成员。

首个内置模板建议为“产品实现小队”：小涛负责人、产品设计、开发实现、质量验证。它是可编辑的成员预设，不表示这些角色已经按 OpenSpec 流程自动协作。模板只提供初始值，创建后与模板无隐式同步。

### 当前团队与角色库

团队管理弹窗分为：

- **当前团队**：查看、编辑、对话、移出成员；项目角色可提升为全局角色。
- **全局角色库**：搜索、邀请、创建和删除全局角色，标明已加入或尚未加入当前项目。

项目角色的编辑只影响当前项目；全局角色的编辑明确影响所有项目。移除有活动任务或运行中对话的成员时，先要求停止相关工作；历史详情保留角色名称和必要快照，避免删除后无法追溯。

### 角色编辑

角色编辑使用同一个表单和实时 3D 预览：

- 名称、职责、可选能力标签；
- 模型偏好；
- 基础造型、主色和辅色；
- 保存范围说明。

外观选项由受控目录提供，不接受任意脚本、外部模型 URL 或项目文件作为可执行 3D 内容。角色ID、历史引用和成员关系不能由外观编辑修改。

## 3D 办公室

### 视觉与空间

采用正交或弱透视的固定斜视镜头，房间包含地面、墙体、工位和资料架。角色、家具和交互物体使用真实空间坐标、深度排序、光照与遮挡；不能用 CSS 位移动画冒充 3D 空间。

第一阶段提供：

- 有限缩放与平移，并有一键复位；
- 桌面与窄屏适配，窗口尺寸变化后重新构图；
- 低多边形人物和少量可区分的基础造型；
- 成员头顶的名称、职责和真实状态标签，遮挡时仍可通过团队列表访问；
- 点击人物或工位选中成员，键盘与团队列表提供等价操作；
- 点击资料架打开现有产物目录。

3D 场景使用经过验证的 WebGL 渲染库和本地打包资源。React 负责页面、弹窗和业务状态，渲染引擎只负责场景；场景失败时显示可读错误和可用的二维团队列表，不能空白或伪造在线状态。

### 状态与动画

人物动画是状态的表现，不是状态来源。运行、等待、失败、空闲均来自后端快照；纯装饰动作不能显示为正在工作。

- 空闲角色可在自己的活动区域内短距离行走或停留，位置来自本地确定性活动路径。
- 忙碌、等待、失败和空闲使用不同姿态及文字标签，不能只靠颜色区分。
- 角色对话、任务状态和资料数量继续来自真实 API。
- 打开操作菜单时暂停该角色的装饰移动，不暂停真实任务。
- 页面不可见时停止渲染循环和轮询；`prefers-reduced-motion` 下关闭装饰移动，保留静态状态。
- 任务执行者按真实任务存在期间展示；结束后离开活动区，任务与产物仍可追溯。

第一阶段不做自由漫游、复杂寻路、人物物理碰撞或装饰动画反向驱动业务状态。

## 共享角色读取协议草案

本节是供实现评审的协议草案，不是已发布的 Skill 契约。第一阶段由客户端写入，后续 Skill 先实现只读发现；写入能力、流程读取和委派需另行评审。

### 存储与归属

建议采用可移植文件作为共享边界，客户端数据库只保存运行状态：

```text
<当前客户端环境数据目录>/collaboration/
  roles/registry.yaml       # 全局角色权威记录

<项目>/.xiaotao/
  roles/registry.yaml       # 项目角色权威记录
  team.yaml                 # 当前项目成员关系
  workflows/                # 后续版本，不在第一阶段创建或伪造
```

正式版与 UAT 的全局目录继续隔离。项目文件不写入已安装 Skill。共享文件采用版本化 schema、UTF-8、稳定 ID 和原子写入；客户端与 Skill 不能一边写 YAML、一边从数据库缓存返回互相矛盾的“权威”结果。

### 最小数据形状

```yaml
schema_version: 1
revision: 12
roles:
  - id: role_product_designer
    name: 产品设计
    scope: project
    responsibility: 梳理需求并形成可审阅的产品方案
    capabilities: [product-discovery]
    model_preference: null
    appearance:
      shape: explorer
      primary: coral
      secondary: sand
```

```yaml
schema_version: 1
revision: 4
members:
  - role_id: role_product_designer
    role_scope: project
    joined_at: 2026-11-13T10:00:00+08:00
```

协议要求：

- 角色注册表和成员关系分别递增 `revision`；读取者发现版本不支持或引用无效时明确报告，不猜测修复。
- 项目角色引用只在当前项目解析；全局角色引用解析当前环境的全局注册表。
- 重复 ID、未知来源、缺失角色、非法外观或模型偏好均返回可诊断错误；模型偏好不构成模型可用性保证。
- 模型偏好与外观只是角色配置，不能授予工具、目录、命令、审批或跨项目记忆权限。
- 写入通过同一份校验和原子替换实现；不得依赖模型生成未经验证的注册表。
- 后续 Skill 查询只加载当前项目的轻量成员目录及被请求角色，不把所有角色的历史对话和项目经历装入上下文。

### Skill 后续读取语义

Skill 在识别当前项目后，可按需获得：当前成员列表、角色职责与外观元数据、已加入的全局角色，以及后续版本中的可用流程。查询结果必须包含注册表版本和诊断信息。

角色被移出或删除后，Skill 不得从历史文本恢复其为当前成员。项目角色不能被其他项目解析；全局角色共享配置，不共享项目经历。纯对话宿主没有独立执行能力时，只能如实使用会话内降级，不得声称角色已独立工作。

## 后续流程与 Skill 重构

工作流程是独立对象，由阶段组成；每个执行阶段必须指派当前项目成员。成员模板与流程模板可以组合推荐，但不互相拥有。

后续需要单独设计：

1. 流程的保存、版本、编辑和成员重新指派；
2. 角色到有界 Worker 的转换及规格快照；
3. 任务中的角色、流程阶段、Worker 和执行会话关联；
4. 客户端与 Skill 的读写冲突、版本兼容和迁移；
5. 项目记忆隔离、任务恢复、权限与降级；
6. Skill 对角色和流程的实际查询与校验。

不能把新增角色目录解释为旧 Role 协议复活，也不能把角色存在等同于流程存在或独立 Agent 已启动。

## 实施拆分

1. **共享角色模型与存储**：版本化 schema、全局与项目注册表、成员关系、原子写入、迁移和错误诊断。
2. **团队管理 API**：模板、角色 CRUD、邀请、移出、提升全局、运行中保护和历史快照。
3. **团队管理前端**：首次建队、当前团队、全局角色库、角色表单和 3D 外观预览。
4. **真实 3D 场景**：本地渲染依赖、房间、人物、交互、状态映射、缩放平移和降级视图。
5. **现有能力接线**：角色对话、真实状态、任务执行者、资料架、轮询生命周期。
6. **协议交接**：冻结第一阶段读取格式，提供 Skill 查询样例和后续重构清单。

## 验收标准

- 从模板和自由创建都能生成真实项目成员，重启后保持；模板默认不产生全局角色。
- 全局角色可加入多个项目，配置修改按确认范围生效；项目角色不泄漏到其他项目。
- 移出、提升和删除不会造成双重身份、丢失历史或静默级联删除。
- 每种造型和配色均可预览、保存并在办公室一致呈现。
- 3D 场景具有真实深度、遮挡、光照和有限镜头操作；点击、键盘和降级列表均可管理团队。
- 页面隐藏停止渲染，减少动态效果生效；WebGL 不可用时仍可访问成员和真实状态。
- 对话、任务和资料使用真实数据，不用装饰动画或预设模板冒充执行状态。
- 共享文件通过 schema、重复引用、跨项目隔离、原子写入和版本兼容测试。
- Go、前端、3D 浏览器测试和 Windows WebView2 实际验收分别记录；浏览器合成测试不冒充真实模型或桌面验收。
